# รับมือเหตุด้านความปลอดภัย / ข้อมูลรั่ว

ใช้เมื่อสงสัยว่า: ข้อมูลลูกค้าหลุด, บัญชีพนักงานถูกใช้โดยคนอื่น, secret หลุด (อยู่ใน git / แชต / screenshot), มีคนยิงระบบผิดปกติ

> ⏱ **PDPA มาตรา 37(4):** เหตุละเมิดข้อมูลส่วนบุคคลต้องแจ้ง สคส. **ภายใน 72 ชม. นับจากรู้เหตุ** เว้นแต่ไม่มีความเสี่ยงต่อสิทธิของเจ้าของข้อมูล
> ถ้าเสี่ยงสูง ต้องแจ้งเจ้าของข้อมูล (ลูกค้า) พร้อมแนวทางเยียวยาโดยไม่ชักช้าด้วย — เริ่มจับเวลาตั้งแต่ข้อ 1

## ผู้รับผิดชอบ

| บทบาท | ใคร | หน้าที่ |
|---|---|---|
| ผู้ตัดสินใจ (incident lead) | _👤 ระบุชื่อ_ | ตัดสินว่าเป็นเหตุจริงไหม, ต้องแจ้ง สคส. / ลูกค้าไหม |
| ผู้ดูแลระบบ | _👤 ระบุชื่อ_ | ปิดทาง, หมุน secret, เก็บหลักฐาน |
| ผู้ติดต่อ สคส. / DPO | _👤 ระบุชื่อ_ | ยื่นแจ้งเหตุ, ร่างข้อความถึงลูกค้า |

## 1. บันทึกทันที (ก่อนแก้อะไร)

เปิดไฟล์บันทึกเหตุ (copy หัวข้อท้ายไฟล์นี้) — เวลาที่รู้เหตุ, ใครพบ, เห็นอะไร
หลักฐานที่ต้องเก็บก่อนมันหาย:

- **audit_log** — หน้า `/admin/audit` (หรือ export ประวัติการใช้งาน) กรองช่วงเวลา/ผู้ใช้ที่สงสัย
  - `EXPORT` = ใครดาวน์โหลด Excel อะไร กี่แถว ตัวกรองอะไร จาก IP ไหน
  - `LOGIN` = เข้าระบบจาก IP / browser ไหน
  - `UPDATE` / `DELETE` / `STATUS` = แก้ข้อมูลอะไร (มีค่าก่อน-หลัง)
- **Render logs** — log ของ Render เก็บไม่นาน ให้ดาวน์โหลดช่วงเวลาที่เกี่ยวข้องเก็บไว้
  - ค้น `requestId`, `track_*` (หน้า `/track` ของลูกค้า), `API 4xx/5xx`
  - IP ใน log และ `track_event` ฝั่ง `/track` เป็น HMAC (`ipHash`) — เทียบได้ว่าเป็น IP เดียวกัน แต่ย้อนกลับเป็น IP ไม่ได้ · IP จริงอยู่ใน `issued_ip` ของ `track_ticket` / `track_otp` / `track_session` / `track_doc_ticket` แค่ช่วงสั้น (ตั๋วผูกกับ IP; ถูกลบเมื่อหมดอายุ) — ดึงเก็บไว้ก่อนถ้าเหตุเพิ่งเกิด
- **Cloudflare** — Security → Events ของช่วงเวลานั้น
- **Supabase** — ถ้าสงสัยว่าเข้าถึง DB ตรง: Logs → Postgres

## 2. ปิดทาง (เลือกตามเหตุ)

| เหตุ | ทำ |
|---|---|
| บัญชีพนักงานถูกใช้โดยคนอื่น / พนักงานออกแล้วยังเข้าได้ | หน้าผู้ใช้ระบบ (`/admin/users`) → กด **ถอนสิทธิ์** ที่แถวนั้น (ตัดสิทธิ์ภายใน ~10 วินาที เพราะสิทธิ์อ่านจาก DB ทุก request) · ให้เจ้าตัวกด "ออกจากระบบ" = ทุกเครื่องของคนนั้นหลุด (`session_version`) · ถ้าบัญชี SSO กลางถูกยึด แจ้งผู้ดูแล SSO ให้ระงับด้วย |
| สงสัยว่า session ของหลายคนหลุด | หมุน `SESSION_SECRET` (ด้านล่าง) = พนักงานทุกคนหลุดพร้อมกัน · ลูกค้าหน้า `/track`: session อยู่ในตาราง `track_session` — ลบแถวทิ้ง (ผ่าน Supabase SQL editor) = ลูกค้าต้องยืนยัน OTP ใหม่ |
| ดาวน์โหลดข้อมูลผิดปกติ | ตำแหน่งนั้น → หน้าสิทธิ์ → เอาสิทธิ์ "ส่งออก Excel" ออก · ดู `EXPORT` ใน audit_log ว่าออกไปแล้วเท่าไร |
| ถูกยิงหนัก / bot | Cloudflare → Security → เปิด Under Attack mode หรือ block IP/ประเทศ · `/track` มี rate limit + Turnstile + เพดาน OTP อยู่แล้ว |
| secret หลุด | หมุน secret นั้นตามตารางด้านล่าง **ก่อน** ลบออกจาก git (ลบจาก git ไม่ได้ทำให้คนที่ได้ไปแล้วใช้ไม่ได้) |
| ช่องโหว่ในโค้ด | แก้ → CI ผ่าน → deploy (migration รันตอน deploy เท่านั้น) · ถ้ารอไม่ได้: ปิด route นั้นชั่วคราวด้วย Cloudflare WAF rule |

## 3. หมุน secret

ตั้งค่าใน Render → Environment แล้ว **Manual Deploy** (ค่า `NEXT_PUBLIC_*` ฝังตอน build → "Clear build cache & deploy")
สร้างค่าสุ่ม: `openssl rand -hex 32`

| Secret | หมุนที่ไหน | ผลข้างเคียงตอนหมุน |
|---|---|---|
| `SESSION_SECRET` | สุ่มใหม่ใน Render | พนักงานทุกคนหลุด ต้อง login ใหม่ (ไม่กระทบลูกค้าหน้า `/track` — ของลูกค้าเก็บใน DB) |
| `DATABASE_URL` (รหัส DB) | Supabase → Database → Reset password → ใส่ใน Render | ระบบล่มช่วงที่ค่ายังไม่ตรงกัน — เปลี่ยนสองฝั่งติดกัน |
| `SUPABASE_SECRET_KEY` | Supabase → API keys → สร้าง secret key ใหม่ → ใส่ Render → deploy → **ลบ key เก่า** | ไฟล์แนบ/สลิปใช้ไม่ได้จนกว่าจะ deploy |
| `SSO_CLIENT_SECRET` | ผู้ดูแล SSO กลางออกให้ใหม่ | login ใหม่ไม่ได้จนกว่าค่าจะตรง (คนที่ login อยู่ไม่หลุด) |
| `CENTRAL_API_KEY` | ผู้ดูแล directory กลางออกให้ใหม่ | ค้นรายชื่อพนักงานตอนผูกอีเมลไม่ได้ชั่วคราว |
| `ORIGIN_AUTH_SECRET` | สุ่มใหม่ → ใส่ **ทั้ง** Render และ Cloudflare Transform Rule `X-Origin-Auth` | ถ้าไม่ตรงกัน ทุก request ได้ 403 — เปลี่ยน Cloudflare ก่อน แล้ว deploy Render ทันที |
| `TRACK_LOG_SECRET` | สุ่มใหม่ใน Render | OTP ที่ส่งไปแล้ว (อายุ 5 นาที) ใช้ไม่ได้ · ตัวนับ rate limit / ล็อก OTP ของ `/track` เริ่มนับใหม่ · `ipHash` ใน log ก่อน-หลังเทียบกันไม่ได้ |
| `TURNSTILE_SECRET_KEY` (+ site key) | Cloudflare → Turnstile → Rotate secret | หน้า `/track` ขอ OTP ไม่ได้จนกว่าค่าจะตรง |
| `THAIBULKSMS_OTP_KEY` / `_SECRET` | ThaiBulkSMS → OTP Manager | ส่ง OTP ไม่ได้จนกว่าค่าจะตรง |

หลังหมุน: เปิด `/api/health` ต้องเป็น ok · login ด้วยบัญชีทดสอบ · ขอ OTP ที่ `/track` หนึ่งครั้ง

## 4. ประเมินว่าต้องแจ้งไหม (ภายใน 72 ชม.)

ตอบให้ได้จาก audit_log / log:

1. ข้อมูลอะไรหลุด — ชื่อ, เบอร์, ที่อยู่, เลขผู้เสียภาษี, รูป/สลิป? มีข้อมูลอ่อนไหว (มาตรา 26) ไหม
2. กี่ราย — นับจาก `meta.rows` ของ `EXPORT` หรือจำนวนแถวที่ถูกอ่าน/แก้
3. ใครได้ไป — คนใน (พนักงาน) หรือคนนอก, ข้อมูลถูกเผยแพร่แล้วหรือยัง
4. เข้ารหัส/ใช้ต่อไม่ได้ไหม (เช่น hash) — ถ้าใช่ ความเสี่ยงต่ำ

- **มีความเสี่ยงต่อสิทธิของเจ้าของข้อมูล** → แจ้ง สคส. ผ่านช่องทางของ สคส. ภายใน 72 ชม. (ยื่นข้อมูลเท่าที่มีก่อนได้ แล้วส่งเพิ่มภายหลัง)
- **เสี่ยงสูง** (เช่น ข้อมูลลูกค้าหลุดออกนอกบริษัท) → แจ้งลูกค้าที่ได้รับผลกระทบด้วย: เกิดอะไร, ข้อมูลอะไร, เราทำอะไรแล้ว, ลูกค้าควรระวังอะไร, ติดต่อใคร
- **ไม่เสี่ยง** → ไม่ต้องแจ้ง แต่ **ต้องบันทึกเหตุและเหตุผลที่ไม่แจ้งไว้** (มาตรา 39 — บันทึกรายการ)

## 5. ปิดเหตุ

- แก้ต้นเหตุ + เพิ่ม test ที่จับเหตุนี้ได้ (bug → test ที่ fail ก่อน)
- ทบทวนสิทธิ์ตำแหน่งที่เกี่ยวข้องในหน้าสิทธิ์
- สรุปเหตุ (ด้านล่าง) เก็บไว้อย่างน้อย 1 ปี
